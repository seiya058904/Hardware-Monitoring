## 停顿证据

旧会话的 Tk 最大心跳间隔为 6,627.88 ms；同一时间窗口整次传感器读取耗时 6,922.95 ms，采样出现 stale。日志未保存该峰值的逐阶段时间戳或精确调用栈。30 秒周期的线程快照比该峰值早约四秒，不能将其中的 `hw.Update` 当作根因。完整命令日志也显示当时升级尝试已提前以失败退出，不能归因于正在运行的安装事务。

独立 20 分钟源码诊断已增加单调时钟、墙钟、线程 ID、线程 CPU 时间及各阶段 begin/end：sensor/native、FPS/进程身份、配置、发布锁及 UI；实际运行 1,202.31 s，无回调异常。网络计数读取最大 1,114.79 ms，与 Tk 1,148.72 ms 心跳间隔重合，独立观察进程同时记录整机 CPU 99.7–100%。[psutil 6.1.0 Windows 源码](https://github.com/giampaolo/psutil/blob/release-6.1.0/psutil/arch/windows/net.c) 在 `GetAdaptersAddresses` 和逐网卡 `GetIfEntry2` 调用期间未释放 Python GIL，存在使其他 Python 线程等待的具体路径；无法由此证明旧 6.63 s 也是该调用。

同一诊断中的稳定阶段：传感器读取中位数 47.26 ms、P99 347.81 ms；配置读取中位数 0.027 ms、最大 22.71 ms；发布锁最大 0.542 ms；FPS 快照最大 15.53 ms；UI 回调 P99 28.67 ms、最大 314.41 ms。这些含诊断开销，不作 before / after 性能收益。LAN 发布阶段没有客户端请求，未得到该阶段的耗时结论。

附加的 WinDLL 网络 API 原型仅在 QA 中运行 600 s，14,696 次逐接口计数调用和前后计数对照通过，没有加入产品。它没有提供旧事件的直接复现，因此未为消除一个未归因数字改动线程结构或采样实现。

风险判断：实际重复运行没有重现 6.63 s 停顿，安静打包复测没有秒级消息响应失败或运行中 HTTP 超时，不能将其判为已证实的持续性发布 blocker。但网络 native 调用持有 GIL 的路径和重负载下较长响应间隔是真实证据，保留偶发卡顿风险；若用户后续实际运行复现，应优先保留同一时刻的阶段与整机负载记录。这不是根因修复或全环境保证。

两个带线程追踪/周期 C 栈转储的 Python 诊断会话发生访问异常；保留了 Windows 错误报告。正常打包运行及取消周期 C 栈转储的阶段诊断没有该异常。异常位置涉及栈/代码行解析，支持诊断工具干扰的解释，但没有 native dump，不能确证；不把失败诊断会话计入稳定性通过。WPR CPU 跟踪开销过大且没有完成有效归因，已停止并精确移除本次生成的 ETL，保留操作记录。
